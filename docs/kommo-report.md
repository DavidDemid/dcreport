# Отчет Kommo: использование и сопровождение

Новый отчет: `/kommo`, существующий PlanFix: `/`. Переключатель меняет маршрут, не объединяет CRM-данные.

## Запуск и проверки

```sh
npm run dev -- --port 3002
npm run test:analytics
npm run test:browser
```
Команды выполнять из корня проекта; открыть `http://localhost:3002/kommo`, тесты запускать в другом терминале.
`test:analytics` проверяет синтетические данные; `test:browser` требует работающий сервер (`REPORT_TEST_URL` меняет адрес).
Необязательные `KOMMO_CSV` и `FINANCE_XLSX` задают пути к локальным фикстурам:
```sh
KOMMO_CSV=/path/to/kommo.csv FINANCE_XLSX=/path/to/finance.xlsx npm run test:browser
```
Без переменных используются пути из `tests/browser/kommo.spec.cjs`; без файлов тест пропускается.
Проверки browser-теста привязаны к конкретной выгрузке, не к произвольным данным.
Авторизация теста читает `AUTH_USERNAME` и `AUTH_PASSWORD` из `.env.local`, если файл есть, иначе из окружения.
Значения учетных данных и исходные таблицы в документацию не включать.

## Импорт и хранение

1. Нажать `Upload Kommo CSV / XLS`: поддерживаются CSV UTF-8, XLSX и XLS.
2. Обязательные заголовки: `ID`, `Lead stage`, `Date Created` или его аналог `Created on`; строки без ID не импортируются. `Modified on` поддерживается как аналог `Last Modified`, исходные заголовки сохраняются для сверки.
3. При необходимости загрузить XLSX/XLS (`Main numbers` или `Actual results`) через `Upload finance report XLS`.
4. Выбрать даты, Services, Channels, Managers и происхождение: all/native/migrated.
   Marketing: обзор, каналы/услуги, конверсии, когорты, финансы, Quality; Sales: обзор, менеджеры, pipeline/response, Next Actions.

Файлы разбираются и сохраняются только в браузере, не отправляются на сервер.
IndexedDB: база `dc-crm-analytics`, хранилище `files`; PlanFix CRM: `crm-v3`,
Kommo CRM: `kommo-v1`. Финансовый ключ `finance-april-2026` общий для обоих отчетов:
повторная загрузка финансов заменяет общий сохраненный файл, восстанавливаемый при открытии.
Если IndexedDB недоступна, Kommo работает с загрузкой в текущей сессии и показывает предупреждение;
после открытия заново потребуется повторный импорт. При блокировке закрыть другие вкладки отчета.

## Очистка и классификация

`Clean leads` включен по умолчанию: исключает явные test-записи, оставляет последнюю запись ID,
объединяет валидный email (иначе телефон от 8 цифр) + одну услугу в пределах 30 дней от первого лида.
Одного имени недостаточно; одиночная запись с маркером дубля не удаляется.
Relevancy берется из последней заполненной оценки рабочей записи; суммы дублей не складываются.
`All CRM rows` отключает очистку; `Reset all filters` возвращает весь период и включает очистку.

- `Relevant`: только `Relevancy = Relevant` после trim и без учета регистра, не стадия.
- Оцененные: `Relevant`, `Not Relevant`, `No Relevant`; пустые и прочие значения: неоцененные.
- `Relevant strict rate` = Relevant / все выбранные лиды, включая неоцененных.
- `Relevant among assessed` = Relevant / оцененные; `Assessment coverage` = оцененные / все лиды.
- `Qualified` определяется датой In work/договора, соответствующей стадией или оплатой, не Relevant.
- Клиент: валидная дата оплаты, положительный Payment 1–3, paid-статус/стадия; `Full paid` проверяет полную оплату отдельно.
- `Agreement sent / later` включает последующие стадии и клиентов, но не доказывает подпись:
  для датированной подписи требуется `Agreement signed at`. Воронка не измеряет переходы между стадиями.

Meta разделена на рекламный канал, чаты и неуточнённую атрибуцию. Значения `Facebook`,
`Instagram` и `Facebook / Instagram` в `Marketing Source` сами по себе не доказывают чат
или рекламу: проверка истории CRM показала такие значения и у отправленных lead forms.
Без других подтверждений источник — `Facebook / Instagram (source unknown)`, а способ
обращения не угадывается. Чат требует явного Messenger/DM/Chat в контексте Meta;
`Facebook ads` обозначает рекламу.
Если UTM/first-touch или платная lead-form подтверждают рекламу, источник остаётся рекламным,
а Messenger/Instagram сохраняется отдельно как способ обращения. Название платформы без
признаков чата или платного привлечения само по себе не доказывает рекламу.
`sourceEvidence` показывает основание классификации в CSV и детализации KPI.
Блок проверки Meta отдельно показывает неуточнённые Meta-лиды с кнопкой «Данные».
Это не оценка количества потерянных рекламных заявок: контакты и имена не используются
для переноса на Ads, внешняя проверочная таблица не нужна для обычной загрузки.
При открытии сайта сохранённый исходный CRM-файл разбирается заново актуальным кодом.
Только рекламный канал сопоставляется с рекламными расходами Meta; SMM/agency/organic
не выдаются за рекламный бюджет, стоимость чатов без расходов остаётся недоступной.

## Даты, когорты и скорость

Migration-флаг: заполнен `Old Lead ID` или `Date Created(from Planfix)`, даже если старая дата некорректна.
Фильтры и месяцы создания используют валидную `Date Created(from Planfix)`, иначе `Date Created` Kommo;
при очистке сохраняется самая ранняя дата группы. Импорт не считается новым привлечением.
Snapshot: последняя допустимая `Date Created`/`Last Modified` файла, не live CRM и не текущее время.
Выбор периода общий для PlanFix и Kommo: готовые диапазоны, ручной ввод, быстрый переход к месяцу/году,
два календаря на компьютере и один на телефоне. `Apply` применяет обе границы одновременно;
`Cancel` и Escape не меняют отчет. В Kommo относительные диапазоны отсчитываются от snapshot,
а не от сегодняшней даты, чтобы исторический файл не давал пустой период. `All time` использует границы CRM.
Можно вручную выбрать более ранний период для финансовой истории. Один день включается целиком.
Даты без часового пояса сохраняют календарное время CRM; рабочий календарь не применяется.
Текущее время для проверки будущих дат берется по локальным часам браузера; предполагается совпадение с часовым поясом CRM.
Некорректные, будущие относительно snapshot и предшествующие созданию даты исключаются из расчетов дат,
не удаляя лид целиком. Дата оплаты без времени допустима в день создания; будущая `Next Task` разрешена.
Когорты M0–M5 показывают накопленную конверсию по календарным месяцам только по валидной дате события;
для оплаты нужны реальные `First payment at`/`Full payment at`, не стадия и не подстановка даты создания.
Ненаблюдаемые горизонты не заполняются; последний наблюдаемый месяц остается неполным.
`Current paid status` учитывает текущие признаки клиента; `Paid date unknown`: клиенты без валидной
первой оплаты. Они не входят в числитель датированной когорты первой оплаты, но остаются в ее базе лидов.

У когорт два режима, общий для верхней таблицы и всех сервисов:
- `Накопленная конверсия, %`: доля всей когорты, достигшая события не позже Mx.
- `Конверсии за месяц, количество`: число лидов, у которых выбранное событие произошло именно в Mx;
  прошлые месяцы не прибавляются. Один лид с датой первой оплаты учитывается в одной ячейке.

Пример: из 10 сентябрьских лидов впервые оплатили 1 в сентябре, 1 в октябре и 2 в ноябре.
Количество по месяцам: `1 / 1 / 2`; накопленные доли: `10% / 20% / 40%`.
При выборе полной оплаты, первого контакта или отправки договора применяется дата соответствующего события,
а не дата первой оплаты. Это число лидов с событием, не реестр всех банковских транзакций.
События после M5 показаны как отдельное пояснение, а не добавлены в последнюю ячейку.
Заголовки M0–M5 и значения центрируются в одинаковых колонках. Контекст когорты отделен от временной матрицы.
Выбранный режим сохраняется при смене языка и применяется к PDF.
Median/p90 считаются по `First contact at - Date Created` только для native Kommo с валидным неотрицательным интервалом.
Coverage скорости = измеренные / все native; SLA% = уложившиеся / измеренные, не все лиды.
Это календарное время записанного первого контакта, не обязательно первого ответа человека.
Менеджер: текущий `Lead resp. user`, не исторический исполнитель; история переназначений не восстановлена.

## Ограничения и финансы

Active-only snapshot без закрытой истории не дает исторический win/rejection rate и полное привлечение.
Причина отказа сама по себе не означает lost; старая `Lost at(from Planfix)` не закрывает активный Kommo-лид.
Возраст pipeline: от создания, не от стадии; Next Actions: рекомендации на snapshot. SLA/Stale after настраиваются, CRM не меняется.
`Sale` и Payment 1–3 имеют неизвестную валюту; Sale не является подтвержденной выручкой или finance EUR.
Recorded CRM Sale суммирует только клиентов, записи с датой подписи или won; оплаты не заменяются Sale.
Финансы: календарные месяцы всей компании, не CRM-когорты; фильтры услуг/менеджеров не распределяют итоги.
Платежные события в финансовом сравнении считаются по месяцу первой оплаты независимо от месяца создания.
Finance дополняет Overview, Channels & Services и Conversions блоком `Acquisition economics / Finance + Kommo`.
Вкладка `Finance & Reconciliation` сохраняет финансовую историю, планы и сверку, а не отдельную CRM-аналитику.
Расходы: совпавшие месяц/канал finance; услуги/кампании/срезы получают оценку по доле лидов в канале и месяце, не фактические расходы.
В `matched months` включаются только полностью выбранные месяцы до месяца snapshot с явно заполненными расходами канала.
`Matched leads`, `Matched clients` и список месяцев показывают покрытие; все выбранные CRM-лиды остаются в обычных отчетах.
`CPL = matched spend / matched leads`, `CPQL = matched spend / matched qualified`, `CAC = matched spend / matched clients`.
Клиенты из других, не покрытых расходами месяцев не уменьшают CAC. Итоговые коэффициенты считаются из сумм, не средних ставок.
При неполном или еще не завершенном на snapshot месяце расходы не пересчитываются пропорционально дням.
Если ни одного совпавшего месяца/канала нет либо знаменатель равен нулю, соответствующая стоимость — `n/a`, не ноль.
Наличие части покрытых месяцев больше не скрывает всю финансовую аналитику за весь CRM-период:
стоимости явно ограничены совпавшей частью. Это предварительный cohort CAC по выгруженным лидам, не полная атрибуция.
Revenue / marketing: общий коэффициент компании, не атрибутированный ROAS канала.

## Визуальные сравнения

Overview показывает привлечение по сервисам и каналам. Channels & Services дополнительно сравнивает
качество лидов, конверсии продуктов, matched CPL/CAC и каналы отдельно внутри каждого сервиса.
Длина полосы привлечения показывает число лидов; цвет — Relevant / Not Relevant / Not assessed.
Конверсии имеют общую шкалу 0–100%; Relevant, Qualified и Client — независимые доли, не последовательные переходы.
Стоимость имеет общую шкалу EUR и использует только финансово покрытые когорты.
Длинные названия переносятся; большие диаграммы разбиваются на самостоятельные блоки для PDF.
Все подробные таблицы сохранены.

В сравнениях каналов показаны две релевантности: `Relevant / all` = целевые / все лиды,
`Relevant / assessed` = целевые / оценённые лиды. Пустые и нераспознанные оценки входят
в первую базу, но не во вторую. Явные отрицательные оценки `Not Relevant` и `No Relevant`
входят в оценённую базу. Без оценённых лидов вторая доля недоступна (`n/a`).
Таблицы показывают числитель и знаменатель под процентом; диаграммы — обе доли рядом.
Глобальные фильтры и отдельный срез услуги применяются к обеим долям одинаково.

Выбор дат ограничен сегодняшним локальным днём браузера: будущие ячейки и переходы
недоступны, ручной ввод будущей даты не применяется. Историческая дата снимка по-прежнему
служит опорой относительных пресетов, но не ограничивает ручной выбор сегодняшнего дня.

## Quality и экспорт

### Оплаты sales по датам событий

Sales Overview и Managers начинаются с отдельного календаря событий. Период применяется
к `First payment at`, `Second payment at`, `Third payment at`, а не к созданию лида.
Лид января с оплатой октября попадает в октябрьские оплаты, но остаётся январской
маркетинговой когортой. Эти sales-блоки видны даже при нуле созданных за период лидов.

В Sales Overview и Managers есть тумблер «Только лиды, созданные в выбранном периоде».
По умолчанию он выключен: календарь событий охватывает лидов любых дат создания.
При включении дата исходного создания дополнительно должна попадать в выбранный период;
даты самих оплат и договоров по-прежнему ограничены тем же периодом. Переключатель влияет
на карточки оплат, таблицы менеджеров/договоров, график, реестр, проверку дат и «Данные».
Режим общий для двух sales-страниц и отражается в PDF. Загрузка новой CRM и сброс фильтров
возвращают режим всех дат создания. Маркетинговая аналитика и её когорты не меняются.

- Первые оплаты: число записей с валидной первой датой в периоде.
- Календарная дата оплаты раньше создания карточки сохраняется в sales с предупреждением:
  CRM могла быть заведена позже платежа. Исходная дата не переписывается, а временные
  маркетинговые когорты по-прежнему исключают отрицательный лаг. Невозможные даты и
  будущие платежи не восстанавливаются.
- Последующие оплаты: вторые и третьи платежи с собственной датой в периоде.
- Оплатившие лиды: разные аналитические сделки с хотя бы одним таким платежом.
- Известная сумма: только соответствующие датам значения `Payment 1/2/3`.
  Пропуски не равны нулю, другая сумма или Sale не подставляются. Нулевые и отрицательные
  записанные суммы сохраняются. Суммы не являются сверкой с банком.
- `Full payment at` — отдельная отметка достижения полной оплаты, не четвёртый перевод.
  Если она раньше последующего платежа, конфликт выводится для проверки.
- Отправленные и подписанные договоры считаются по соответствующим датам.
  `Retainer sent` без даты показывается отдельно за всю историю; оплаты без retainer
  не превращаются автоматически в датированную отправку или подпись договора.
- Стадия и Last Modified не восстанавливают месяц платежа. Раздел проверки дат охватывает
  всю историю при текущих фильтрах, потому что неопределённую дату нельзя отнести к месяцу.

Менеджер — текущий ответственный из снимка CRM. Исторический ответственный при платеже
неизвестен. Все фильтры, кроме замены даты создания на дату события в этих блоках, сохранены.
Режим очистки задаёт аналитические сделки; исходные дубли не суммируются повторно.
Для одного объединённого платежа разные исходные даты исключаются как конфликт;
при одной дате и разных суммах количество сохраняется, сумма остаётся неизвестной.

Ниже остаются исходные показатели по когортам создания, с явными подписями. Marketing,
когорты и общий фильтр создания не изменены. CSV-заголовки `Respons. user`, `Lead sale €`,
`Fullname` и контактные поля без `(contact)` поддерживаются наряду с XLSX-заголовками;
исходные заголовки сохраняются для проверки качества.

Quality сравнивает `Selected`/`All supplied`: точные заголовки, заполненность, даты/proxy-only, ошибки дат, миграцию, response, атрибуцию.
Отсутствующий столбец: `Unavailable`, не пустой; заполненность не означает валидность или конверсию.
Источник и способ захвата разделены: Calendly/Website form не доказывают рекламный канал.
PDF создается локально в A4 landscape из отдельного скрытого export-представления, чтобы широкие таблицы оставались читаемыми.
Глобальные фильтры, событие когорты, выбранный канал тренда, поиск и страница очереди сохраняются в PDF.
`Export this page to PDF`: `dc-kommo-{marketing|sales}-{page}_{from}_to_{to}.pdf`;
`Export full PDF`: `dc-kommo-full-report_{from}_to_{to}.pdf`. Даты: выбранный период `YYYY-MM-DD`,
при пустых границах: `start`/`end`; PlanFix экспортируется отдельно, с префиксом `dc-crm-analytics-`.
CSV выгружает выбранные лиды или отфильтрованную очередь; содержит контактные данные, распространять ограниченно.
Основные правила: `lib/kommo.ts`, `lib/kommo-analytics.ts`; интерфейс: `components/kommo-report.tsx`,
`components/kommo-views.tsx`, `components/kommo-quality.tsx`; хранение/PDF: `lib/report-files.ts`, `lib/report-pdf.ts`.

## Язык интерфейса

В верхней панели доступен выбор English / Русский. Выбор хранится локально в браузере
(`dc-report-language`) и применяется к Kommo, общим элементам PlanFix и странице входа.
Язык меняет отображение, но не исходные значения CRM, идентификаторы, фильтры, группировку или формулы.
Точные названия экспортируемых полей остаются исходными там, где это необходимо для сверки.
Пояснения доступны у информационных значков. Для русских PDF заголовки рисуются браузерным шрифтом,
чтобы кириллица не повреждалась стандартным PDF-шрифтом.

## Детализация KPI

Под карточками показателей видны пояснения. У основных CRM-показателей в Overview,
Conversions, Sales Overview и Cohorts есть кнопка `Data` / `Данные`.
Она открывает боковую панель с формулой, текущим срезом, полями расчёта и конкретными лидами.
Список строится по тем же правилам, что и карточка, без повторной очистки данных.
У процентов отдельно доступны числитель и база расчёта; у Relevancy также есть группы
неоценённых и явно нерелевантных лидов. Поиск и CSV работают по выбранной группе.
Раскрытие записи показывает значения полей, основной ID и ID объединённых записей.
Для Kommo доступна история нормализованных записей до объединения; она может включать
записи за пределами фильтра дат и не является дополнительными лидами в KPI.
Без адреса CRM ссылки на карточки не выдумываются: ID можно скопировать и найти в CRM.
Данные остаются в браузере. Кнопки и открытая панель не включаются в PDF.
В PlanFix детализация подключена к основным CRM-карточкам Overview и Conversion;
финансовые показатели не подменяются списком CRM-лидов.

## Проверка Meta-заявок

Channels & Services содержит блок `Meta: acquisition source vs form records`. Он работает только
на текущей Kommo-выгрузке и не требует файла из Ads Manager. Сравниваются выбранная когорта
создания CRM и вся история. Канальный фильтр для этого диагностического блока явно снят;
услуги, менеджеры, происхождение и режим очистки остаются прежними.

Подтверждённая платная форма требует FB lead ID и явного `Fb is organic = false`.
Уникальный ID заявки не равен шаблону `FB form id`; один шаблон может дать множество заявок.
Повторные Meta ID и разные контакты на одном ID отмечаются для проверки, без автоматического
удаления людей или изменения источника. Кнопки данных доступны для выбранной когорты и всей истории.
Отсутствующий столбец даёт недоступный показатель, а не ноль. Время отправки формы не выводится
из даты создания CRM-лида. Поэтому этот блок не заменяет помесячную статистику отправок форм.
